## Real problems found and fixed during the build (not hypothetical)

These are included specifically because a generic "AI wrote this, please review it"
disclosure is easy to skim past. These are concrete evidence of what actually happened:

1. **A real, disclosed security vulnerability in the initial dependency pin.**
   `npm install` surfaced a deprecation warning for `next@14.2.15` pointing to a real
   CVE chain (CVE-2025-55184, CVE-2025-55183) disclosed by the Next.js team on December
   11, 2025 — a Denial of Service and Source Code Exposure vulnerability affecting App
   Router applications specifically, which is this project's entire architecture. This
   was investigated (not assumed), the official advisory was fetched and read, and the
   dependency was bumped to `14.2.35`, the confirmed patched release. See
   `docs/security-checklist.md` for the full account.

2. **A genuine bug in error-status mapping.** While writing the API test for "rejects a
   correction with no reviewer_note," the missing-note validation failure was found to
   fall through to a generic 500 response instead of a proper 400 — a real
   correctness issue (a client input error was being reported as a server error), not
   just a missing test. Fixed by adding a dedicated `MissingReviewerNoteError` class and
   mapping it explicitly in the route handler, then confirming the test now asserts the
   correct status code.

3. **A test-fixture bug that looked like a production bug.** Two domain tests failed on
   first run with `UnconfirmedRecordError`, even though both records had
   `human_decision: 'confirmed'`. Rather than weaken the schema to make the tests pass,
   the actual cause was diagnosed directly (a temporary debug test isolated the exact
   Zod validation failure): the test fixtures used plain strings like `'img-9'` as
   `image_id` instead of real UUIDs, and the schema's `uuid()` check — working as
   designed — correctly rejected them. The test fixtures were fixed to use
   `randomUUID()`, not the schema.

4. **A path-resolution bug in the test config**, caught when the first test run failed
   to resolve the `@/` import alias for test files. Traced to `tsconfig.json` excluding
   `tests/**/*`, which `vite-tsconfig-paths` was respecting. Fixed by including tests in
   the main tsconfig rather than working around it with a separate config.

5. **A build failure isolated to a sandbox limitation, not a code defect.** The first
   `npm run build` failed while fetching Google Fonts, because this build environment's
   network policy blocks `fonts.googleapis.com` (confirmed directly with `curl`, which
   returned a `403` from the sandbox's own egress proxy, not a real connectivity
   failure). To confirm no other bug was hiding behind this, the font loading was
   temporarily removed, the build was re-run and passed completely, and the real
   Google Fonts implementation was then restored. This will build normally in any
   environment with normal internet access (a real dev machine, CI, or Vercel), which
   nearly every real environment has.

6. **A dead Gemini model name, found only by running the app for real.** The Gemini
   adapter was originally hardcoded to `gemini-2.0-flash`. That model was fully shut
   down by Google on June 1, 2026. Every single request silently failed over to the
   Groq fallback — 0% confidence, "no visual analysis was possible," identical for
   every image regardless of content — with no error visible anywhere, because the
   fallback succeeded and only a total-chain failure was being logged. This is exactly
   the category of bug the test suite structurally cannot catch (the fake test adapter
   never calls a real model name), and it was only found because the person running
   this project deployed it with real API keys and noticed every result looked
   identical, then asked about it directly. Fixed by (a) updating the default model to
   `gemini-2.5-flash` and (b) adding a `console.error` log for every individual
   provider failure in `analyzeAndRoute()`, not just for total-chain failure — so the
   next time a provider silently degrades, it's visible in server logs immediately
   instead of only being detectable by noticing every result looks the same.

## What genuinely could not be done, and why

- **No real Gemini or Groq API call was made.** No API key was available in the build
  environment. The adapters are written correctly against the documented SDK shapes but
  are unverified against live traffic.
- **No Vercel deployment was performed.** This requires a human with account access.
- **No real adversarial test images were produced** for the prompt-injection evaluation
  cases — these are described in text in the evaluation fixture and need to be created
  and tested by the team.
- **The individual code defense cannot be performed by an AI.** See
  `SETUP_AND_NEXT_STEPS.md` §6.

## What the team must do before claiming this as their own work

explain and modify it without this document open. A scaffold that runs and passes its
tests is a real, verified starting point — it is not, by itself, evidence that the team
